英文原标题：PRINS or TLS on N32: how 5G roaming security is really negotiated between SEPPs

On the N32 interface between two Security Edge Protection Proxies, 3GPP gives operators a choice of exactly two protection mechanisms, and the choice is not cosmetic. Either the two SEPPs establish TLS directly to each other, in which case nothing in between can read or alter the roaming traffic, or they negotiate PRINS, the protocol for N32 interconnect security, in which case the payload is protected at the application layer with JSON Web Encryption and a roaming intermediary is explicitly permitted to modify a defined subset of information elements and sign those modifications with JSON Web Signature. The short answer to which one an operator should use is that TLS is correct whenever no intermediary needs to touch the content, and PRINS is the only correct option when one does. Choosing TLS while still expecting an intermediary to mediate the traffic is not a security posture, it is a contradiction that gets resolved in the intermediary's favour. That distinction is where a lot of 5G standalone roaming deployments are quietly imprecise, and it is why the N32 interface deserves a closer look than the architecture diagram gives it. This article goes one level below our overview of SEPP security in 5G roaming and examines what the N32-c handshake actually negotiates, how a PRINS protected message is constructed, what the protection policies do and do not cover, where real deployments diverge from the specification, and what a security team should verify at the interconnect edge. The relevant specifications are 3GPP TS 33.501 for the security architecture, 3GPP TS 29.573 for the protocol and API detail, and the GSMA NG.113 5GS roaming guidelines for the interoperability profile the industry actually implements. What N32 is and why it has two security modes N32 is the inter PLMN interface that carries service based interface signalling between a visited network and a home network in 5G standalone roaming. It exists because the 5G core replaced the point to point signalling of earlier generations with HTTP/2 and JSON over a service based architecture, and that architecture had to be extended across an operator boundary without simply exposing internal network functions to a foreign network. The SEPP is the single point of entry and exit for that traffic, and N32 is the pipe between two SEPPs. The interface is split into two logical parts. N32-c is the control part, a mutually authenticated TLS connection between the two SEPPs used for capability negotiation, key material establishment, policy exchange and context management. N32-f is the forwarding part, which carries the actual roaming signalling: the Nudm, Nausf, Namf and other service requests and responses that a visited network needs to make against a home network for registration, authentication, subscription retrieval and session management.
