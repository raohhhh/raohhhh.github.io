英文原标题：eSIM IoT remote provisioning security: what SGP.32, the eIM and the IPA change

SGP.32 changes eSIM security for IoT by taking the human out of the provisioning loop. In the consumer model defined by GSMA SGP.22, a person holds the device, opens a local profile assistant and consents to a profile download. In the IoT model defined by GSMA SGP.31 and SGP.32, that consent is replaced by a remote server, the eSIM IoT remote Manager (eIM), whose signed instructions the eUICC accepts with no local confirmation. The cryptography underneath is largely inherited from SGP.22 and well understood. What is new is that a single management platform can now enable, disable and delete profiles across an entire fleet, and that the device-side component which used to be a user interface is now an unattended agent running in the device application environment. That shift matters for operators, IoT connectivity platforms and enterprises running private networks, because the blast radius of a compromised provisioning path is no longer one handset. It is every module the eIM is authorised to manage, which in industrial deployments means tens or hundreds of thousands of devices in places nobody wants to visit. This article covers what SGP.32 specifies, where the trust boundaries moved, which failure modes deserve attention in an assessment, and what an operator can observe from the network side once profiles start moving. What SGP.32 is, and how it relates to SGP.02 and SGP.22 SGP.32 is the GSMA technical specification for eSIM remote provisioning in IoT devices, sitting alongside SGP.31, which carries the architecture and requirements. It is the third remote SIM provisioning family the GSMA has produced, and understanding why it exists requires knowing what the first two could not do. SGP.02 was the original machine-to-machine specification. It put the operator in charge through a Subscription Manager Secure Routing platform that pushed profiles to the eUICC, often over SMS or CAT-TP bearers. It still runs a very large installed base, but the push model assumed an operator relationship enterprises found restrictive, and the bearer choices aged badly as legacy networks were switched off, removing the transport a lot of older M2M provisioning quietly depended on. Our note on the phasing out of 2G and 3G networks covers the wider consequences of that retirement. SGP.22 solved the commercial problem by putting the subscriber in control through a Local Profile Assistant, and it introduced the SM-DP+ and the bound profile package that remain the core of profile protection today. Its problem for IoT is structural: SGP.22 assumes there is a user interface and a user, and a water meter in a basement has neither. SGP.32 keeps what works, retaining the SM-DP+, the bound profile package and the ES8+ and ES9+ interfaces toward it, and replaces what assumed a person. The entity that decides a profile operation should happen becomes the eIM. The entity on the device that carries it out becomes the IoT Profile Assistant, or IPA.
