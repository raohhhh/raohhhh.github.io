英文原标题：DNS security in mobile networks: node selection, roaming resolution and the 3gppnetwork.org namespace

DNS is a load-bearing part of every mobile core, and it is almost never in scope when an operator commissions a security assessment. Node selection in the EPC and in the 5G core depends on it, home-routed roaming depends on it, IMS and interconnect depend on it, and the whole thing runs on a namespace, 3gppnetwork.org , that is deliberately resolvable from outside the operator. The short answer to why this matters: DNS is an unauthenticated input to decisions about which gateway carries a subscriber's traffic, and in most networks nothing downstream re-verifies the answer it returned. This post walks through what DNS actually decides inside a mobile network, how resolution flows across GRX and IPX, the failure modes that show up repeatedly in assessments, and the testing and detection work that closes them. It is written for core network engineers, roaming teams and security teams who already know their network topology and want to understand where the resolution layer sits in their risk picture. The relevant specifications are 3GPP TS 29.303 for the DNS procedures themselves, TS 23.003 for the naming formats, and GSMA IR.67 for the operational guidelines that govern GRX and IPX resolution. What DNS actually decides inside a mobile core Inside a mobile core, DNS is not a convenience for humans. It is the mechanism by which one network function discovers the address of another, and in the EPC it is the mechanism by which a session is bound to a specific gateway. 3GPP TS 29.303, titled Domain Name System Procedures, Stage 3, defines this formally: it specifies how an MME, SGSN or SGW resolves an APN into a set of candidate gateways, and how a 5G SMF resolves the user plane functions it can select for a given data network. The mechanism is Straightforward NAPTR, or S-NAPTR, defined in IETF RFC 3958. A node queries for NAPTR records under a constructed name, filters the results by service parameters that encode the interface and protocol it wants, follows the chain to SRV or A and AAAA records, and ends up with an ordered candidate list. The order matters: the NAPTR order and preference fields determine which gateway is tried first. Whoever controls the answer controls the selection. That is the part worth sitting with. In a conventional enterprise network, a poisoned DNS answer sends a user to the wrong web server and TLS usually catches it. In a mobile core, a wrong answer can influence which user plane function or PDN gateway terminates a subscriber session, and the protocols that follow, GTP-C and PFCP among them, carry no certificate-based identity check that would notice. The transport is trusted because the network is assumed to be closed. It is not closed, and it has not been for a long time.
