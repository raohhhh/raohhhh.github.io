英文原标题：Emergency call security in mobile networks: unauthenticated access, NIA0 and caller location

An emergency call is the one session a mobile network has to complete when everything else about the subscriber is in doubt. The device may have no valid subscription, the USIM may be absent or rejected, and the subscriber may be barred or roaming-restricted. Regulation in most markets requires the call to be connected anyway, and 3GPP has built deliberate exceptions into the access, core and IMS layers to make that possible. Those exceptions are the direct answer to why emergency handling deserves its own security review: the emergency path is a legitimate, standardised bypass of authentication, barring and in some configurations ciphering and integrity protection, and it runs in production on every mobile network. This article walks through how an emergency session is actually established in LTE and 5G, why unauthenticated emergency access and the null algorithms NIA0 and NEA0 exist, how caller location reaches the public safety answering point, and where these mechanisms create exposure an operator can measure and monitor. The argument is not that emergency services are insecure by design. It is that the emergency path has a different trust model from the rest of the network, that its security properties are defined mostly by availability, and that it is routinely left out of scope when operators plan signalling and IMS and SIP assessments. What makes an emergency call different from every other call An emergency call is different because the network must accept it from a device it has not verified, and because the priority order of security properties is inverted. In ordinary sessions an operator optimises for confidentiality and integrity first and treats availability as an engineering concern. In emergency handling, availability is the regulatory obligation, and confidentiality and integrity are preserved only where doing so does not block the call. Every design decision in the emergency path follows from that inversion. Three concrete consequences flow from it. First, the network must support emergency attach and registration procedures separate from the normal ones, so that barring, roaming restrictions and subscription checks can be skipped. 3GPP TS 23.167, which specifies IMS emergency session architecture, is explicit that when a UE performs an emergency registration, barring and roaming restrictions are ignored. Second, the network must serve a device with no credentials at all, which means there is no shared key to derive ciphering and integrity keys from. Third, the network must obtain and forward a location accurate enough to route the session to the correct answering point, which pulls the positioning architecture into the emergency trust boundary. Each is a reasonable answer to a hard regulatory problem. Each also widens the set of states a core network can legitimately be driven into by an unauthenticated peer.
